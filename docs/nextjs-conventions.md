# Next.js Conventions

This project runs **Next.js 16.3.5 (App Router)** with **React 19**. This version has
breaking changes vs. older Next.js knowledge — the rules below call out the ones
that matter most for this codebase. When in doubt, check
`node_modules/next/dist/docs/` before assuming an older API still applies.

## Proxy, not Middleware

- The `middleware.ts` file convention is **deprecated**. This project uses
  **`proxy.ts`** at the repo root instead.
- Do not create a `middleware.ts` file. Add proxy logic to the existing
  [proxy.ts](../proxy.ts).
- Keep the `matcher` config's negative-lookahead pattern intact when editing it —
  it excludes static assets from Clerk's proxy so CSS/JS/images keep loading.

## `params` and `searchParams` are Promises

- In `page.tsx` and `layout.tsx`, `params` and `searchParams` are `Promise`s and
  must be awaited (or unwrapped with React's `use()` in Client Components).
- Prefer the generated global helper types over hand-written prop types:
  - Pages: `export default async function Page(props: PageProps<'/blog/[slug]'>)`
  - Layouts: `export default function Layout(props: LayoutProps<'/dashboard'>)`
- These `PageProps<...>` / `LayoutProps<...>` types are globally available and
  generated by `next dev`, `next build`, or `next typegen` — no import needed.
  If a newly created route's types aren't recognized yet, restart the dev
  server or run `next typegen`.

## Server Components by default

- Components are Server Components unless they need hooks, event handlers, or
  browser-only APIs — only then add `"use client"` at the top of the file.
- Never import the Drizzle `db` client (see [database.md](./database.md)) into a
  Client Component.

## Metadata

- Use the `Metadata` type / `generateMetadata` export for `<title>`, `<meta>`,
  and OG tags. Do not hand-write `<head>` tags in `layout.tsx` or `page.tsx`.

## Root layout

- [app/layout.tsx](../app/layout.tsx) is the single root layout and owns the
  `<html>`/`<body>` tags, fonts, and the `ClerkProvider`. Don't duplicate these
  in nested layouts.

## File conventions in use

- `page.tsx`, `layout.tsx` — standard route/layout files.
- `app/sign-in/[[...sign-in]]/page.tsx`, `app/sign-up/[[...sign-up]]/page.tsx` —
  Clerk's optional catch-all convention; keep these exact paths (see
  [auth.md](./auth.md)).
- Add `loading.tsx` / `error.tsx` per route segment only when a segment
  actually needs a loading or error boundary — don't scaffold them speculatively.
